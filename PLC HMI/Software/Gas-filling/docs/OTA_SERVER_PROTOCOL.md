# پروتکل به‌روزرسانی سرور و استاندارد انتشار فریمور (OTA Server Protocol & Release Standard)
## Dual-Partition OTA Architecture, LASTFILE Protocol & Hash Validation Directive

این سند تشریح‌کننده ساختار فنی کلاینت به‌روزرسانی آنلاین (`GasFilling_HMI/ota_manager.cpp`)، قالب توصیف‌گر انتشار سرور (`lastfile`) و الزامات ارتقای امن دستگاه گاز پرکن هافلر است.

---

## ۱. معماری حافظه و پارتیشن‌های دوگانه (Dual OTA Partitioning)

دستگاه دارای ۱۶ مگابایت حافظه فلش با جدول پارتیشن‌بندی دوگانه امن (`partitions.csv`) است:

```
+-------------------------------------------------------------------------+
|                              16 MB FLASH MAP                            |
+-------------------------------------------------------------------------+
| 0x00000 - 0x07FFF | Bootloader (32 KB)                                  |
| 0x08000 - 0x08FFF | Partition Table (4 KB)                              |
| 0x09000 - 0x0DFFF | NVS Storage / Parameters / Locks (20 KB - PRESERVED)|
| 0x0E000 - 0x0FFFF | otadata / Boot Partition State (8 KB)               |
| 0x10000 - 0x70FFFF| app0: OTA Partition 0 (7 MB - Active App)           |
| 0x710000- 0xE0FFFF| app1: OTA Partition 1 (7 MB - Target OTA App)       |
| 0xE10000- 0xFFFFFF| Spiffs / Storage (Remaining ~1.9 MB)                |
+-------------------------------------------------------------------------+
```

### مزایای حیاتی معماری Dual-OTA:
1. **عدم پاک شدن پارامترها و قفل‌ها:** پارتیشن NVS در آدرس `0x9000` کاملاً مستقل بوده و هنگام ارتقای نرم‌افزار دست‌نخورده باقی می‌ماند (تنظیمات، ساعات کارکرد و قفل روزشمار حفظ می‌شوند).
2. **رول‌بک خودکار در صورت خطا (Fail-Safe Rollback):** اگر در هنگام دانلود فریمور برق دستگاه قطع شود یا فایل مخدوش باشد، چیپ همچنان از پارتیشن قبلی بوت شده و دستگاه هرگز "بریک" (Brick) نمی‌شود.
3. **اعتبارسنجی قطعی هش SHA-256:** سفت‌افزار دانلود شده بلافاصله قبل از فعال‌سازی با هش درج شده در فایل `lastfile` مطابقت داده می‌شود.

## ۲. مشخصات کلاینت آپدیت سرور (`ota_manager.cpp`)

- **آدرس سرور مرکزی هافلر:** `http://ota.haffler-infi.ir` بر روی پورت متنی HTTP 80 (اجتناب از سربار رم mbedTLS SSL بر روی پردازنده).
- **وظیفه پس‌زمینه در Core 0:** عملیات دانلود و هش در یک تسک مجزای FreeRTOS روی هسته ۰ پردازنده با استک ۸ کیلوبایت اجرا می‌شود تا صفحه گرافیکی LVGL در هسته ۱ بدون کوچک‌ترین افت فریم به کار خود ادامه دهد.
- **استریم باینری ۱۶ کیلوبایتی:** داده‌ها در بافرهای ۱۶ کیلوبایتی استریم شده و مستقیماً روی فلش نوشته می‌شوند.

هر بسته انتشار بر روی سرور شامل دو فایل کنار هم است:
1. `firmware.bin` (فایل باینری سفت‌افزار)
2. `lastfile` (فایل متنی بدون پسوند با استاندارد ثابت)

## ۴. نمایش لاگ تغییرات تجمیعی به اپراتور (Cumulative Changelog Display)

یکی از وجوه تمایز دستگاه هافلر این است که وقتی اپراتور در HMI دکمه «بررسی آپدیت» را می‌زند:
1. دستگاه ابتدا فایل `lastfile` را دریافت می‌کند.
2. نسخه جاری نصب‌شده روی دستگاه را با نسخه سرور مقایسه می‌کند.
3. **تمام تغییرات بین نسخه جاری و نسخه جدید** را خط به خط در مدال آپدیت به زبان فارسی نمایش می‌دهد (حداکثر ۱۳ کلمه در هر خط).
4. تنها پس از تایید اپراتور، دانلود فایل حجیم `firmware.bin` آغاز می‌شود.
