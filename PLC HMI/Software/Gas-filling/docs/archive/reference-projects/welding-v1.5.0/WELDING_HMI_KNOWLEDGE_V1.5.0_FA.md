## پوشهٔ `release/` — خروجی نهایی هر بیلد (الزامی)

**قانون:** بعد از **هر** `pio run` موفق، اسکریپت `tools/copy_release_artifacts.py` خودکار **`release/`** را با **فقط فایل‌های لازم** پر می‌کند و فایل‌های اضافی (مثل `firmware.elf`، `pins` تکراری، `VERSION.txt`) را **حذف** می‌کند.

| فایل | حجم تقریبی | کاربرد |
|------|------------|--------|
| `firmware.bin` | ~۵.۳ MB | OTA + esptool @ `0x10000` |
| `bootloader.bin` | ~۱۵ KB | esptool @ `0x0` |
| `partitions.bin` | ~۳ KB | esptool @ `0x8000` |
| `pinmap.txt` | <۱ KB | کنار `firmware.bin` روی سرور OTA |
| `FLASH_ESPTOOL.txt` | متن | دستور `write_flash` |
| `README.txt` | متن | نسخه + تاریخ بیلد |

**عمداً داخل `release/` نیست:** `firmware.elf`، `*.map`، `.pio/` — فقط برای دیباگ/addr2line در `.pio/build/esp32-s3-devkitc-1/` می‌مانند.

**سرور OTA:** فقط `firmware.bin` + `pinmap.txt`

**فلش کارخانه (esptool):**
```text
esptool.py --chip esp32s3 --port COM17 --baud 921600 write_flash ^
  0x0      bootloader.bin ^
  0x8000   partitions.bin ^
  0x10000  firmware.bin
```

**فایل `pins` در ریشهٔ پروژه:** هر بار GPIO/نام I-O عوض شد → ویرایش کن؛ بیلد خودکار در `release/pinmap.txt` کپی می‌شود.

برای هر اصلاح مربوط به کندی صفحه، FPS، CPU، گیج ها، اسکرول، کیبرد، وایفا یا بافر نمایشگر، اول فایل زیر خوانده شود:

## 7.5) قوانین سرعت/روانیِ نمایشگر (حتماً رعایت شود تا سرعت کم نشود)

علتِ اصلیِ کندی: **بازرسمِ هر-فریمیِ ویجت‌ها**. هر بار که در `tick_screen_*` روی یک آبجکت `set_style_*` یا `set_pos/size` یا `set_text` بزنی، آن آبجکت باطل و دوباره رسم می‌شود؛ اگر هر فریم تکرار شود، LCD کند می‌شود.

قوانین پایدار:
1. **استایل را فقط یک‌بار ست کن، نه هر فریم.** الگوی `perf_style_once(obj)` در `screens.c` را نگه دار و استفاده کن (توابع `keep_main_value/title_label_visible` با همین گارد سبک شده‌اند).
2. **متن را فقط هنگام تغییر ست کن:** از `set_label_if_changed(obj, txt)` استفاده کن، نه `lv_label_set_text` مستقیم در tick.
3. ویجت سنگین `lv_meter` فقط هنگام **تغییر مقدار** آپدیت شود و مقدار **پله‌ای** (مثلاً هر ۵ درجه) تا هر فریم بازرسم نشود.
4. **سایه (`shadow_*`)** و **گرادیانِ پس‌زمینه** سنگین‌اند؛ روی المان‌هایی که زیادشان بازرسم می‌شود استفاده نکن. دایرهٔ مرکزی تو‌پر (بدون گرادیان/سایه) نگه داشته شود.
5. `transform_zoom` روی فونت‌های فارسی این پروژه = خراب‌شدن/محوِ متن؛ برای بزرگ‌کردن از فونت واقعی استفاده کن نه zoom.
6. بافر رسم LVGL در RAM داخلی (سریع) و بزرگ نگه داشته شود (`SCREEN_WIDTH*SCREEN_HEIGHT/6`, دابل‌بافر). این برد PSRAM ندارد.
7. **`pushPixelsDMA` در `my_disp_flush` استفاده نشود** — تست شد و صفحهٔ اصلی بالا نیامد؛ `pushColors(..., true)` پایدار است.
8. هرچه روی `screen_menu` اضافه می‌کنی، اگر در tick هر فریم آپدیت می‌شود، حتماً با گاردِ «تغییر/یک‌بار» محافظت کن.

## 7.6) لاگِ بررسیِ کندیِ نمایشگر (کشف‌های قطعی — برای جلوگیری از تکرار)

### کشف‌های تأییدشده
1. **فرم‌ویر درست بالا می‌آید.** با تستِ «رنگِ Haffler سبز» ثابت شد؛ حتی گاهی **بدونِ خاموش/روشنِ دستی، به‌محضِ پروگرم‌شدن** تغییر دیده شد. پس «تغییری نکرد» ربطی به نرسیدنِ فرم‌ویر ندارد.
2. **هشدارِ تستِ نامرئی:** تغییراتِ سرعت چون **ظاهری ندارند**، برای اثباتِ اجرای فرم‌ویرِ نو باید یک **مارکرِ دیداری** (مثل رنگِ Haffler) گذاشت. نکته: «Haffler» **سه لایه** است (obj18 + دو کپیِ faux-bold روی آن)؛ برای تست باید **هر سه** رنگ شوند وگرنه لایهٔ رویی نتیجه را می‌پوشاند.

### کارهایی که انجام شد ولی **هیچ اثری روی سرعت نداشت** (پس گلوگاه این‌ها نیست)
- کم‌کردنِ بازرسمِ هر-فریمی (گاردِ `perf_style_once`، `set_label_if_changed`).
- پله‌ای‌کردن و گیت‌کردنِ `lv_meter` + کم‌کردنِ تیک‌ها (۶۱→۴۵→۲۴) + تبدیل فیل به قوس.
- حذف سایه/گرادیانِ دایره، بافرِ رسمِ بزرگ‌تر (`/6`).
- **throttleِ `ui_tick` از ~۳۰۰–۱۰۰۰Hz به ۲۰Hz** (در `tasks.h`؛ قبلاً هر فریمِ رندر اجرا می‌شد چون `LVGL_DELAY_MIN_MS=1`). این کار **اصولی است و باید بماند**، ولی به‌تنهایی کندی را حل نکرد.
- `Wire.setClock(400000)` برای I2C تاچ.

### بن‌بست‌ها / نکاتِ منفی
- **`pushPixelsDMA` در flush → صفحهٔ اصلی بالا نیامد (خرابی).** فعلاً استفاده نشود؛ `pushColors(..., true)` پایدار است. (DMA باید با تنظیمِ درستِ swap/بافر دوباره و با دقت تست شود.)

### مظنون‌های باقی‌مانده (قدم بعدی)
- چون منطق/رندرِ آبجکت‌ها اثر نداشت، احتمالاً گلوگاه: **throughput فلشِ SPI نمایشگر**، یا **رقابتِ باسِ SPI با ترموکوپل MAX6675** (در `heater_task`)، یا **تأخیرِ تاچ**.
- **ابزارِ تشخیص:** `LV_USE_PERF_MONITOR 1` در `lv_conf.h` روشن شد تا FPS/CPU واقعی خوانده شود:
  - FPS پایین + CPU بالا → کارِ سنگینِ منطقی/تسکِ دیگر.
  - FPS پایین + CPU پایین → گلوگاهِ flush/SPI.
  - FPS بالا → کندیِ واقعی = تأخیرِ تاچ/آپدیت، نه رندر.

## 7.7) جمع‌بندیِ نهاییِ بررسیِ سرعت (۱۲+ ساعت تست — تا گم نشود)

### اندازه‌گیریِ قطعی (با `LV_USE_PERF_MONITOR`)
- **FPS ≈ ۵–۹، CPU ≈ ۹۲–۹۴٪.** یعنی یک **رسمِ کاملِ صفحه ~۱۰۰–۲۰۰ms** طول می‌کشد.
- در حالتِ بی‌کاری (بدون مانیتور) هیچ flushی نیست → بی‌کاری سریع است؛ کندی فقط هنگام **رسمِ نواحیِ بزرگ** (گذارِ صفحه، بازشدنِ کیبورد، پنل‌ها) حس می‌شود.

### چیزهایی که تست شد و **هیچ اثرِ معناداری نداشت** (پس مقصر نیستند):
1. مخفی‌کردنِ `lv_meter` → FPS ۵ ماند.
2. مخفی‌کردنِ **کلِ گیج دما** → فقط ۵→۹ (جزئی).
3. غیرفعال‌کردنِ کاملِ خواندنِ تاچ (`my_touchpad_read` زودبازگشت) → FPS ۵ ماند، CPU ۹۴٪. **پس تاچ/I2C مقصر نیست.**
4. `LV_INDEV_DEF_READ_PERIOD` ۵→۳۰ms → بی‌اثر.
5. `LV_COLOR_16_SWAP=1` + `pushColors(...,false)` (انتقال swap از flush به رندر) → بی‌اثر روی FPS. **پس byte-swap هم گلوگاه نبود.** (این تنظیم درست است و ماند.)
6. throttleِ `ui_tick` (۳۰۰–۱۰۰۰Hz → ۲۰Hz)، گاردِ `perf_style_once`، `set_label_if_changed`، گیت/پله‌ای‌کردنِ متر، کم‌کردنِ تیک‌ها، حذف سایه، بافرِ بزرگ‌تر، هسته‌بندیِ تسک‌ها (LVGL تنها روی Core 1) — **هیچ‌کدام FPS را بالا نبرد.**

### نتیجه‌گیریِ قطعی
- گلوگاه **نه CPUِ منطق است، نه رندرِ آبجکت‌ها، نه تاچ** — بلکه **throughputِ خودِ انتقالِ پیکسل روی SPI به نمایشگر** است. سرعتِ مؤثر خیلی کمتر از ۸۰MHzِ تنظیم‌شده است (یک رسمِ کاملِ صفحه ~۱۰۰ms).
- **تنها راه‌حلِ واقعی: DMA** (تا CPU درگیرِ انتقال نشود و رندرِ بافرِ بعدی با انتقالِ فعلی هم‌پوشانی کند).

### وضعیتِ DMA
- تست شد ولی صفحهٔ اصلی **سفید/معلق** ماند. علتِ محتمل: ناهماهنگیِ byte-order (`setSwapBytes` + `LV_COLOR_16_SWAP=0`).
- **حالا که `LV_COLOR_16_SWAP=1` است، DMA باید بدون `setSwapBytes` درست کار کند** — این مسیرِ پیشنهادیِ بعدی برای سرعت است (با `tft.initDMA()` در setup و `tft.pushPixelsDMA(...)` در flush). باید با حوصله و مارکرِ رنگی تست شود.

### نکاتی که برای حفظِ سرعت باید بماند (در اصلاحاتِ بعدی خراب نشود)
- `LV_COLOR_16_SWAP=1` بماند و در flush از `pushColors(..., false)` یا `pushPixelsDMA` استفاده شود (نه `..., true`).
- بافر بزرگ در RAM داخلی، `ui_tick` با throttle، گاردهای `perf_style_once`/`set_label_if_changed`، متر پله‌ای — همه بمانند.
- از رسمِ کاملِ صفحهٔ غیرضروری پرهیز شود (هر چیزی که نواحیِ بزرگ را invalidate می‌کند سرعت را پایین می‌آورد چون هر رسمِ کامل ~۱۰۰ms است).

## 8) مشکل حیاتی «تغییرات روی صفحه دیده نمی‌شود» (و راه‌حل قطعی)

### علامت
- بعد از `Build` و `Upload` موفق (با `Hash of data verified`)، صفحهٔ نمایشگر هیچ تغییری نشان نمی‌دهد.

### وضعیت واقعی
- در حالت عادی، auto-reset بعد از فلش (`Hard resetting via RTS pin`) **درست کار می‌کند** و حدود ۱ دقیقه‌ای کد روی برد می‌نشیند و خودش بالا می‌آید — نیازی به خاموش/روشن دستی نیست.
- فقط در موارد نادر (برد در حالت گیر، یا ری‌استِ ناقص) ممکن است فرم‌ویرِ جدید بلافاصله اجرا نشود.

### راه‌حلِ پشتیبان (فقط در صورت بروز مشکل)
- اگر بعد از Upload موفق، تغییری روی صفحه دیده نشد، **یک‌بار برد را دستی خاموش/روشن کنید** تا فرم‌ویرِ جدید حتماً بوت شود.
- این فقط یک fallback است، نه روال همیشگی.

## بهینه‌سازیِ سرعتِ LCD (V.1.4.8) — اشتباهاتی که نباید تکرار شوند
- **بافرِ رندرِ LVGL هرگز در PSRAM نباشد.** قبلاً دو بافرِ فول‌اسکرین با ps_malloc در PSRAM بود؛ PSRAM برای رندر (دسترسیِ تصادفیِ مکرر) بسیار کند است و علتِ اصلیِ لگ بود. درست: دو بافرِ ~۱/۸ صفحه در SRAMِ داخلی با heap_caps_malloc(MALLOC_CAP_DMA|MALLOC_CAP_INTERNAL).
- **flush باید DMA باشد.** قبلاً tft.pushColors(...,false) بلاک‌کننده بود (CPU تا پایانِ کلِ انتقالِ SPI بیکار). درست: tft.initDMA() یک‌بار در setup، و در flush: dmaWait()→startWrite→setAddrWindow→pushPixelsDMA→endWrite→lv_disp_flush_ready. هم‌پوشانیِ رندر و انتقال.
- **سواپِ بایت:** lv_conf دارد LV_COLOR_16_SWAP=1، پس tft.setSwapBytes(false) (هم‌ارزِ pushColors swap=false). اگر رنگ‌ها خراب شد این را برعکس کن.
- **حلقهٔ lvgl_task:** LVGL_DELAY_MIN_MS را پایین نگه‌دار (۴ms) تا تا نزدیکِ نرخِ رفرش (LV_DISP_DEF_REFR_PERIOD=16 ≈ ۶۰fps) روان شود؛ MAX=۳۰ برای بی‌کاری. مقدارِ بالای MIN (مثلِ ۲۰) سقفِ FPS را پایین می‌آورد.
- SPI از قبل ۸۰MHz است (سقفِ ILI9341). CPU پیش‌فرض ۲۴۰MHz.
- نکتهٔ بعدی اگر هنوز کند بود: LV_MEM_CUSTOM در PSRAM است (MALLOC_CAP_SPIRAM)؛ انتقالِ آن به داخلی رندرِ پیچیده را تند می‌کند ولی ریسکِ کمبودِ RAM دارد (درختِ بزرگِ صفحات).

> اصلاحیه: DMA flush (initDMA + pushPixelsDMA) روی این بوردِ HSPI/ESP32-S3 صفحه را کاملاً سیاه کرد و برگردانده شد. flushِ سالم = tft.pushColors((uint16_t*)&color_p->full, w*h, false). بُردِ سرعت از بافرِ داخلی + حلقهٔ سریع به‌دست آمد، نه DMA. DMA را کورکورانه دوباره امتحان نکن.

## بخشِ ۰ — جریانِ خودکارِ F5-بوت → رمز → وای‌فای → کارت‌های نصب

### چه چیزی از قبل بود
- نگه‌داشتنِ F5 (کلیدِ آنالوگِ پنل، باندِ ۱۱۰۰-۱۴۰۰) موقعِ بوت، از قبل `set_var_ota_enable(true)` می‌کرد (`checkBoot()` در `general.h`، صدا زده‌شده در `setup()`).
- صفحهٔ `SCREEN_ID_SCREEN_PASSWORD` (کیبردِ `frameware_password_keybord`) از قبل رمز را چک می‌کرد (`action_admin_password_redy` در `main.cpp`) ولی **هیچ‌جا ناوبری نمی‌کرد** — فقط `set_var_is_admin_password_verifyed(true)` می‌شد و همان‌جا می‌ماند.
- صفحهٔ `SCREEN_ID_SCREEN_WIFI` کامل و کارکردی بود (اسکن/اتصال واقعی) ولی به‌صورتِ خودکار بعد از رمز باز نمی‌شد.
- بعد از اتصالِ موفقِ وای‌فای در `ota_task` (تسکِ جدا که فقط وقتی `ota_enable=true` ساخته می‌شود)، خطِ `eez_flow_set_screen(SCREEN_ID_SCREEN_FRAMWARE, ...)` **کامنت شده بود** — یعنی بعد از اتصال هیچ‌جا نمی‌رفت.
- صفحهٔ `SCREEN_ID_SCREEN_FRAMWARE` (۹ کارتِ محصول با آیکون) و دانلود/فلشِ واقعی (`httpUpdate.update`) از قبل کاملاً کار می‌کردند — فقط رسیدن به این صفحه دستی/شکسته بود.

### چه چیزی اضافه شد (۲۰۲۶-۰۷-۰۲)
1. در `setup()` — بعد از `ui_init()`، اگر `ota_enable` است **و** ثبت‌نامِ اولِ بوت تمام شده، مستقیم `eez_flow_set_screen(SCREEN_ID_SCREEN_PASSWORD, ...)`.
2. در `lock_overlay_timer_cb` (نخِ LVGL، هر ۵۰ms) — رصدِ لبهٔ بالارونده‌ی `get_var_is_admin_password_verifyed()`: اگر `ota_enable` است و همین حالا رویِ `SCREEN_ID_SCREEN_PASSWORD` هستیم، برو `SCREEN_ID_SCREEN_WIFI`. (متغیرِ تاییدشدن را پاک نمی‌کنیم — شاید جای دیگری هم به آن وابسته باشد؛ فقط لبهٔ محلی رصد می‌شود.)
3. در `ota_task` (`tasks.h`) — بعد از اتصالِ موفق، اگر `g_pending_self_check` نبود (یعنی این مسیرِ F5-بوت است، نه بروزرسانیِ درجای صفحه اطلاعات)، پرچمِ `g_ota_go_framware_request` را true می‌کند؛ همین پرچم در `lock_overlay_timer_cb` (نخِ LVGL) خوانده و `eez_flow_set_screen(SCREEN_ID_SCREEN_FRAMWARE, ...)` صدا زده می‌شود — چون `ota_task` خودش مستقیم نمی‌تواند LVGL را لمس کند.

### تست
این جریان فقط با **نگه‌داشتنِ فیزیکیِ کلیدِ F5 حینِ روشن‌کردنِ دستگاه** قابلِ‌تست است — از راهِ نرم‌افزار/شبیه‌سازی قابلِ‌تحریک نیست. اگر کار نکرد:
- سریال را چک کن ببین `checkBoot()` اصلاً `ota_enable=true` کرده یا نه (باندِ آنالوگِ F5 ممکن است رویِ این برد کمی فرق داشته باشد).
- چک کن آیا `storage.isCompanyAsked()`/`isAdminAsked()` هر دو true هستند (وگرنه اول صفحه‌های ثبت‌نام باز می‌شود، نه رمز — این عمدی است).
- اگر رمز درست وارد شد ولی به وای‌فای نرفت: `eez_flow_get_current_screen() == SCREEN_ID_SCREEN_PASSWORD` را چک کن؛ شاید صفحه از راهِ دیگری (نه ناوبریِ ماژولِ بالا) باز شده و این شرط پاس نمی‌شود.

1. **`lv_textarea_set_one_line(ta, true)` خودش ارتفاعِ کادر را `LV_SIZE_CONTENT` می‌کند** و مقدارِ `lv_obj_set_size` را override می‌کند. اگر ارتفاعِ کادرِ رمز دوباره به حالتِ بزرگِ پیش‌فرض برگشت، علتش همینه — باید بعد از `set_one_line` دوباره `lv_obj_set_height(ta, H)` صدا زده شود.

3. **کیبردِ `lv_textarea` با هر لمس، مکان‌نما را جابه‌جا و متن را اسکرول می‌کند** (تابعِ داخلیِ `update_cursor_position_on_click` در `lv_textarea.c`، مستقل از فلگِ `SCROLLABLE`). چون این دو کادر فقط با کیبردِ سفارشی پر می‌شوند (نه تایپِ مستقیم)، در `admin_setup_ta_cb` روی `PRESSED/PRESSING/RELEASED/FOCUSED/CLICKED` مکان‌نما به `LV_TEXTAREA_CURSOR_LAST` قفل و اسکرول به صفر برمی‌گردد؛ همین کار بعد از هر `add_text`/`del_char` هم در `admin_setup_kb_key_cb` تکرار می‌شود. مکان‌نمای چشمک‌زن هم مخفی شده (`LV_PART_CURSOR` → `LV_OPA_TRANSP`).
4. **کادرِ اول با فوکوس، تمِ FOCUSED جدا می‌گیرد** (outline/shadow/border/bg متفاوت از DEFAULT) و بزرگ‌تر به‌نظر می‌رسد. برای هر دو کادر، استایلِ FOCUSED دقیقاً برابرِ DEFAULT ست شده (`border/bg/outline/shadow`).
5. کیبردِ رمز از نقشهٔ مشترکِ `get_pass_keyboard_map()`/`pass_keyboard_ctrl` (در `screens.c`، دیگر `static` نیست) استفاده می‌کند — همان کیبردِ عددیِ «پاک کردن/تایید» که در صفحه‌های دیگرِ رمز هم هست. کیبرد به هیچ textareaـی وصل نیست (`lv_keyboard_set_textarea(kb, NULL)`)؛ همهٔ ورودی دستی در `admin_setup_kb_key_cb` مدیریت می‌شود.

## بخشِ ۲ — جابجاییِ پایهٔ ورودی/خروجی از منوی اطلاعات

### ایده
هر خروجی (میز/پرس‌چپ/پرس‌راست/المنت/شابلون/SSR/تقویت۱/تقویت۲) و هر گروهِ ورودی (سنسورِ المنت/شابلون/میز، اضطراری، پدال) به‌جای `#define` ثابت، حالا **متغیرِ سراسریِ زمانِ‌اجراست** (`include/defines.h`: `extern int TABLE, ...`؛ تعریفِ واقعی با مقدارِ پیش‌فرض در `src/main.cpp`). مقدارِ ذخیره‌شده در `storage.loadPinMap()` — که در `setup()` **پیش از** `setupPin()` صدا زده می‌شود — رویِ این متغیرها می‌نشیند.

### چرا نیازی به ری‌استارت نیست
- همهٔ کدِ سیکلِ جوش (`tasks.h`) مستقیم `digitalWrite(TABLE, ...)` و مثل آن را صدا می‌زند — یعنی هر بار مقدارِ *فعلیِ* متغیر را می‌خواند، نه یک کپیِ قدیمی.
- `pinMode`/`analogSetPinAttenuation` در `setupPin()` (`include/general.h`) روی **مجموعهٔ ثابتِ فیزیکیِ پایه‌ها** (۸ خروجی + ۵ ورودی) یک‌بار سرِ بوت اعمال می‌شود — مستقل از این‌که کدام نام صاحبِ کدام پایه است. پس جابجاییِ نام↔پایه در همین مجموعه نیازی به تنظیمِ سخت‌افزاریِ دوباره ندارد.
- تنها جایی که یک کپیِ محلیِ خطرناک پیدا شد: `disp_sensor_task` در `main.cpp` سه پایهٔ سنسور را در یک آرایهٔ محلی کپی می‌کرد که فقط سرِ استارتِ تسک خوانده می‌شد. حالا با **پوینتر** به خودِ متغیرها کار می‌کند (`int *pins[3] = {&SENSOR_ELEMENT, &SENSOR_SHABLON, &SENSOR_TABLE};`) — اگر بازنویسی شد، همین را دوباره چک کن (`grep "= *{.*TABLE\|ELEMENT\|SHABLON" در main.cpp/tasks.h` برای کشفِ کپی‌های جدید).

- نگه‌داشتنِ ۲ ثانیه رویِ عنوانِ ستونِ «خروجی»/«ورودی» (نه یک نامِ خاص) → `io_reset_dialog_open(isOutput)` — دقیقاً هم‌سبکِ دیالوگِ ریستِ چهارچوب (`frames_reset_dlg`): تأیید چپ، نوارِ ۵ثانیه‌ایِ انصراف راست. تأیید → همهٔ پایه‌های همان دسته به `PIN_CANDIDATES_OUT/IN[i]` (پیش‌فرضِ خودشان) برمی‌گردند؛ چون این مقادیر در هر دسته یکتا هستند، تداخلِ دو نام روی یک پایه ساختاری غیرِممکن است. ۵ ثانیه بدونِ تأیید → فقط بسته می‌شود (کنسل، نه تأیید).

# دانش فنی جامع بهینه سازی سرعت نمایشگر HMI

- تاریخ ثبت و بازنویسی: 2026-06-30
- پروژه نمونه: `D:\V.1.4.8_fixpack_2026-06-23`
- سخت افزار هدف: `ESP32-S3` با LCD، تاچ، LVGL، EEZ، PSRAM و فلش 16MB/16N2
- کاربرد: این سند فقط مخصوص این نسخه نیست. برای تمام پروژه های PLC/HMI شرکت که روی همین سخت افزار یا ساختار مشابه اجرا می شوند قابل استفاده است.

## 1) خلاصه مهم

کندی صفحه در این نوع HMI معمولا از «ضعیف بودن LCD» یا «کند بودن CPU خام» نیست. علت اصلی این است که برنامه در هر tick، آبجکت های زیادی از LVGL را بی دلیل تغییر می دهد و LVGL مجبور می شود بخش بزرگی از صفحه را دوباره رندر کند.

قانون اصلی:

```text
هر چیزی که تغییر نکرده، نباید دوباره به LVGL ست شود.
هر چیزی که ثابت است، باید در create ساخته شود نه در tick.
هر چیزی که فقط یک عددش عوض شده، نباید باعث redraw کل صفحه یا گیج های دیگر شود.
```

در صفحه اصلی این پروژه ثابت شد که نمایشگر و پردازنده توان سرعت بالا را دارند، چون صفحه لوگو به `FPS=62` می رسد. کندی از ترکیب آبجکت های سنگین، رفرش تکراری و invalidate زیاد در صفحه اصلی و بعضی صفحات تنظیمات بود.

## 2) برداشت درست از CPU و FPS

در LVGL عدد `FPS` فقط وقتی معنی کامل دارد که صفحه واقعا در حال redraw باشد. اگر صفحه بیکار است و هیچ چیزی تغییر نمی کند، FPS پایین می تواند طبیعی باشد، چون LVGL لازم نمی بیند فریم جدید بکشد.

برداشت درست:

- `CPU بالا + FPS پایین`: مشکل واقعی. یعنی برنامه دارد کار زیاد می کند ولی خروجی کند است.
- `CPU پایین + FPS پایین در حالت بیکار`: الزاما بد نیست. ممکن است یعنی redraw لازم نیست.
- `FPS بالا ولی CPU بالا`: ممکن است redraw مصنوعی یا بی دلیل انجام می شود.
- معیار نهایی برای HMI: تاچ، باز شدن کیبرد، اسکرول، تغییر مقدار گیج و دمو باید سریع حس شوند.

پس برای تست سرعت، فقط به idle FPS نگاه نکن. این موارد را جدا تست کن:

- صفحه ثابت بدون لمس
- لمس و کشیدن مقدار گیج
- باز شدن کیبرد عددی
- اسکرول صفحه اطلاعات
- شروع سیکل و تغییر چراغ ها
- دمو ورود به صفحه اصلی

## 3) نتایج تست عملی همین پروژه

این اعداد نشان می دهند مشکل از کدام ناحیه بوده و چطور باید فکر کرد:

| حالت تست | نتیجه تقریبی | معنی فنی |
| --- | --- | --- |
| صفحه لوگو/اسپلش | `CPU=8`, `FPS=62` | سخت افزار و LCD توان سرعت بالا دارند. |
| صفحه اصلی کامل با سه گیج | `CPU=91..92`, `FPS=4..5` | مشکل از رندر UI صفحه اصلی است. |
| مخفی شدن کل اجزای صفحه اصلی | `CPU=4..5`, `FPS=62` | منطق کلی برنامه گلوگاه اصلی نبود. |
| مخفی شدن پایین صفحه + گیج دما | حدود `CPU=35`, `FPS=29` | ترکیب گیج دما و پایین صفحه سنگین است. |
| پایین صفحه + فقط گیج جوش بالا | حدود `CPU=18`, `FPS=62` | یک گیج تنها قابل تحمل است. |
| پایین صفحه + فقط گیج خنک کاری پایین | حدود `CPU=19`, `FPS=62` | مشکل از مجموع اجزا و redraw تکراری است. |
| فقط نوار پایین صفحه | حدود `CPU=52`, `FPS=20` | چراغ ها/نوار پایین اگر هر tick style بگیرند سنگین می شوند. |

نتیجه: راه حل حذف ظاهر نیست؛ راه حل این است که همان ظاهر با update دقیق و محدود اجرا شود.

## 4) علت های عمومی کندی در پروژه های LVGL/ESP32-S3

### 4.1 ست کردن متن تکراری

`lv_label_set_text` حتی اگر متن همان متن قبلی باشد می تواند آبجکت را invalidate کند. اگر label روی گیج یا کنار آبجکت سنگین باشد، هزینه آن خیلی زیاد می شود.

الگوی درست:

```c
static void set_label_if_changed(lv_obj_t *obj, const char *txt) {
    if (!obj || !txt) return;
    const char *cur = lv_label_get_text(obj);
    if (!cur || strcmp(cur, txt) != 0) {
        lv_label_set_text(obj, txt);
    }
}
```

### 4.2 ست کردن style در هر tick

توابعی مثل اینها نباید در loop/tick بدون شرط اجرا شوند:

```c
lv_obj_set_style_bg_color(...)
lv_obj_set_style_text_font(...)
lv_obj_set_style_text_opa(...)
lv_obj_set_style_border_width(...)
lv_obj_set_style_opa(...)
```

اینها باید فقط هنگام تغییر واقعی اجرا شوند. برای style ثابت، یک helper مثل `perf_style_once` استفاده کن.

### 4.3 تغییر flag/position/size بدون نیاز

حتی `lv_obj_add_flag`, `lv_obj_clear_flag`, `lv_obj_set_pos`, `lv_obj_set_size` اگر بی دلیل تکرار شوند می توانند باعث layout/repaint شوند.

الگوی درست:

```c
static void obj_add_flag_if_needed(lv_obj_t *obj, lv_obj_flag_t flag) {
    if (obj && !lv_obj_has_flag(obj, flag)) lv_obj_add_flag(obj, flag);
}

static void obj_clear_flag_if_needed(lv_obj_t *obj, lv_obj_flag_t flag) {
    if (obj && lv_obj_has_flag(obj, flag)) lv_obj_clear_flag(obj, flag);
}
```

### 4.4 آبجکت های سنگین: lv_meter، arc، mask، shadow، clipping

گیج های دایره ای، نیم دایره ها، خط چین های زیاد، shadow، opacity و mask جزو بخش های سنگین LVGL هستند. اگر مقدار یک گیج عوض شد، نباید گیج های دیگر یا کل صفحه redraw شوند.

قانون:

- شکل ثابت گیج یک بار ساخته شود.
- فقط fill/needle/عدد همان گیج تغییر کند.
- مقدار سنسور زنده لازم نیست هر 20ms روی گیج سنگین بنشیند.
- برای گیج دما می توان مقدار را quantize کرد، مثلا هر 10 یا 30 درجه فقط fill را تغییر داد، اما عدد مهم را سریع تر نشان داد.

### 4.5 invalidate کل صفحه

این الگو در tick تقریبا ممنوع است:

```c
lv_obj_invalidate(objects.screen_menu);
```

اگر مجبور شدی invalidate کنی، آبجکت کوچک هدف را invalidate کن، نه کل صفحه.

### 4.6 ساختن و حذف کردن آبجکت در مسیر پرتکرار

ساخت/حذف مداوم label، button، lamp، list item، keyboard یا popup سنگین است. آبجکت های پرتکرار باید ساخته شوند و فقط hide/show یا value آنها تغییر کند.

### 4.7 کارهای کند در UI tick

این موارد نباید در tick سریع صفحه انجام شوند:

- اسکن WiFi
- خواندن سنسورهای کند یا چند نمونه ای
- `temperatureRead` زیاد
- خواندن RTC/DS3231 در هر فریم
- کارهای فایل سیستم، SPIFFS، OTA
- build/rebuild لیست های بزرگ
- لاگ سریال زیاد

اینها باید task جدا، timer کند، state machine یا callback داشته باشند.

## 5) بافر نمایشگر کند می کند یا سریع؟

جواب کوتاه: خود بافر لازم است؛ محل و اندازه بافر مهم است.

در ESP32-S3 با LVGL:

- بافر render اگر در PSRAM باشد، برای LVGL کند می شود، چون LVGL دسترسی تصادفی و زیاد دارد.
- بافر خیلی کوچک باعث تعداد flush زیاد می شود.
- بافر خیلی بزرگ اگر در PSRAM برود یا RAM داخلی را کم کند، کندی و ناپایداری می آورد.
- بهترین حالت عملی در این پروژه: دو بافر داخلی DMA-capable با اندازه حدود `SCREEN_WIDTH * 32`.
- PSRAM برای فایل ها، تصویرهای بزرگ، cache کم اهمیت یا داده های کم استفاده خوب است؛ برای draw buffer فعال LVGL انتخاب اول نیست.

نکته مهم این پروژه:

- مسیر DMA روی بعضی ترکیب های Arduino/TFT_eSPI صفحه را سیاه می کرد، پس `pushColors(..., false)` به عنوان مسیر سالم نگه داشته شد.
- DMA را فقط وقتی فعال کن که با تصویر واقعی تست شده باشد. سرعت بیشتر بدون تصویر سالم ارزشی ندارد.
- تغییر `LV_COLOR_16_SWAP`, `setSwapBytes`, `pushImageDMA`, `pushColors` و اندازه بافر حتما باید روی LCD واقعی تست شود.

## 6) معماری درست صفحه در HMI

هر صفحه باید دو بخش ذهنی داشته باشد:

### create screen

فقط یک بار هنگام ساخت صفحه:

- ساخت آبجکت ها
- تنظیم style ثابت
- ساخت پس زمینه، خط چین ها، label ثابت، آیکون ها
- ساخت event callback ها
- ساخت keyboard/popup اگر قابل reuse است

### tick screen

در هر tick فقط:

- خواندن state فعلی
- مقایسه با state قبلی
- اعمال تغییر فقط روی آبجکت هایی که واقعا عوض شده اند

الگوی ذهنی:

```text
state جدید را حساب کن
با state قبلی مقایسه کن
فقط diff را به LVGL بده
state قبلی را آپدیت کن
```

## 7) الگوی عمومی tick سریع

```c
void tick_screen_x(void) {
    static uint32_t last_tick = 0;
    uint32_t min_period = user_is_interacting ? 40U : 150U;

    if (last_tick != 0 && lv_tick_elaps(last_tick) < min_period) {
        return;
    }
    last_tick = lv_tick_get();

    int32_t new_value = get_value();
    static int32_t old_value = INT32_MIN;
    if (new_value != old_value) {
        old_value = new_value;
        lv_arc_set_value(objects.my_arc, new_value);
    }

    const char *new_text = get_text();
    set_label_if_changed(objects.my_label, new_text);
}
```

نکته: برای کنترل هایی که کاربر در حال لمس آنهاست، مقدار اصلی باید فوری آپدیت شود. throttle برای کارهای پس زمینه و UI سنگین است، نه برای حس مستقیم تاچ.

## 8) قانون «تاچ فوری، پس زمینه کندتر»

در HMI کاربر باید وقتی مقدار را کم/زیاد می کند، عدد و حس کنترل فوری باشند. اما لازم نیست همه چیز همان لحظه redraw شود.

الگوی درست:

- عدد وسط گیج: فوری
- مقدار داخلی برنامه: فوری
- fill یا needle سنگین: در صورت امکان فوری برای همان گیج، اما با جلوگیری از redraw گیج های دیگر
- سنسور زنده و دماهای فرعی: با فاصله بیشتر
- label های ثابت و زبان: فقط هنگام تغییر زبان

مثال کاربردی:

```text
کاربر گیج زمان جوش را تغییر می دهد:
1. عدد وسط همان گیج فوری تغییر کند.
2. arc همان گیج فوری تغییر کند.
3. گیج دما، گیج خنک کاری، لامپ ها و نوار پایین هیچ کاری نکنند مگر state خودشان عوض شده باشد.
```

## 9) گیج ها و راه حل های مخصوص آنها

### 9.1 گیج زمان

- مقدار time arc فقط اگر عوض شد ست شود.
- عدد وسط گیج در event تاچ، دکمه مثبت/منفی و keyboard فوری set شود.
- خط چین های ثابت نباید دوباره ساخته شوند.
- اگر گیج با `lv_arc_set_value` سنگین شد، فقط همان arc تغییر کند و title/label اطراف دست نخورد.

### 9.2 گیج دما

گیج دما معمولا سنگین ترین بخش است، چون fill چند رنگ، خط چین، needle و عدد دارد.

راه حل های مجاز:

- needle اگر برای کاربر مهم نیست حذف شود.
- fill زنده دما با coalescing آپدیت شود، مثلا هر 1000ms یا وقتی تغییر معنی دار دارد.
- target temperature هنگام لمس کاربر فوری آپدیت شود.
- مقدار live sensor با quantize نمایش داده شود تا هر نوسان کوچک باعث redraw نشود.
- عدد هدف/عدد مهم باید سریع باشد، حتی اگر fill دما کندتر آپدیت شود.

### 9.3 دمو ورود به صفحه

دمو اگر همه گیج ها را با قدم های ریز حرکت دهد، عملا خودش یک benchmark سنگین می شود.

راه حل:

- قدم های دمو را درشت تر کن.
- tick دمو را کندتر از لمس کاربر بگذار.
- لامپ های پایین را در دمو مصنوعی روشن/خاموش نکن، مگر سناریو واقعا لازم دارد.
- فقط گیج هایی که دیده می شوند و باید حرکت کنند update شوند.

## 10) چراغ ها، نوار پایین و خروجی های PLC

چراغ ها ساده به نظر می رسند، اما اگر هر tick رنگ، opacity، position و animation آنها set شود، سنگین می شوند.

قانون:

- برای هر چراغ `last_state` نگه دار.
- فقط چراغی که state آن تغییر کرده style بگیرد.
- برای نیمه روشن/نیمه پر بودن چراغ های سنسوردار، درصد/position را cache کن.
- اگر خروجی خاموش است و سناریو می گوید چراغ سنسور خاموش باشد، همان حالت دقیق حفظ شود.
- `lv_anim_del` و ساخت animation فقط هنگام تغییر واقعی، نه هر tick.

الگوی bit diff برای صفحه اطلاعات یا چراغ های PLC:

```c
static uint8_t prev_bits = 0xFF;
uint8_t new_bits = read_inputs_as_bits();

if (new_bits != prev_bits) {
    uint8_t changed = new_bits ^ prev_bits;
    prev_bits = new_bits;

    for (int i = 0; i < 8; i++) {
        if ((changed >> i) & 1) {
            lv_obj_set_style_bg_color(lamps[i],
                (new_bits >> i) & 1 ? color_on : color_off,
                LV_PART_MAIN | LV_STATE_DEFAULT);
        }
    }
}
```

## 11) صفحه اطلاعات و صفحات اسکرولی

اسکرول باید اولویت داشته باشد. وقتی کاربر دارد صفحه را می کشد، لازم نیست همان لحظه همه ورودی/خروجی ها و دماها آپدیت شوند.

راه حل:

- روی container اسکرولی callback بگذار.
- زمان آخرین scroll را ذخیره کن.
- تا 200 تا 400ms بعد از scroll، update سنگین را skip کن.
- فقط dialog/timer ضروری را ادامه بده.

الگوی عمومی:

```c
static uint32_t scroll_last_tick = 0;

static void scroll_cb(lv_event_t *e) {
    if (lv_event_get_code(e) == LV_EVENT_SCROLL) {
        scroll_last_tick = lv_tick_get();
    }
}

void tick_info_screen(void) {
    bool recent_scroll = scroll_last_tick != 0 &&
                         lv_tick_elaps(scroll_last_tick) < 300U;
    if (recent_scroll) {
        tick_dialogs_only();
        return;
    }

    update_only_changed_io_lamps();
    update_slow_info_labels();
}
```

## 12) صفحات تنظیمات

صفحات تنظیمات معمولا از نظر ظاهری ساده اند، اما dropdown، textarea، switch، slider و keyboard اگر بی دلیل refresh شوند کند می شوند.

قوانین:

- متن ثابت تب ها فقط هنگام تغییر زبان update شود.
- `lv_dropdown_set_options` فقط وقتی options عوض شده و dropdown باز نیست اجرا شود.
- `lv_slider_set_value` فقط وقتی مقدار فرق کرده اجرا شود.
- `lv_textarea_set_text` هنگام تایپ کاربر نباید از tick دوباره overwrite شود.
- وقتی پنل ویرایش باز است، جدول پشت آن را refresh نکن.
- keyboard را در مسیر تاچ سنگین نساز. اگر ممکن است reuse یا سریع show/hide کن.

الگوی پنل ویرایش:

```c
bool edit_panel_visible = panel && !lv_obj_has_flag(panel, LV_OBJ_FLAG_HIDDEN);
if (edit_panel_visible) {
    update_panel_labels_only_if_changed();
    if (!panel_was_visible) load_values_once();
    panel_was_visible = true;
    return; // جدول پشت پنل refresh نشود
}
panel_was_visible = false;
update_table_if_changed();
```

## 13) وایفا، اسکن و وب اپ

وایفا اگر در همان مسیر UI tick یا callback سنگین اجرا شود می تواند صفحه را قفل کند. اسکن WiFi باید مرحله ای و غیرهمزمان باشد.

قوانین عمومی:

- AP/WebApp و حالت scan/STA را جدا مدیریت کن.
- وقتی وارد منوی انتخاب WiFi می شوی، اگر لازم است موقتا از حالت AP خارج شو یا `WIFI_AP_STA` را درست تنظیم کن تا scan واقعی انجام شود.
- `WiFi.scanNetworks(true)` برای scan async مناسب تر است.
- UI فقط وقتی نتیجه آماده شد لیست را بازسازی کند.
- هنگام اسکن، فقط یک label کوچک مثل "Searching..." تغییر کند، نه کل صفحه.
- لیست SSID ها را هر tick پاک و دوباره نساز.
- بعد از خروج از منوی WiFi، اگر تنظیمات می گوید WebApp/AP روشن باشد، دوباره به حالت AP/وب اپ برگرد.

این نکته برای پروژه های PLC مهم است: کاربر ممکن است همزمان با روشن بودن AP دستگاه، بخواهد شبکه های اطراف را اسکن و انتخاب کند. حالت WiFi باید روشن، شفاف و state-machine باشد؛ نه اینکه در حالت web app گیر کند.

## 14) سنسورها، ADC، RTC و تسک ها

هر خواندن سخت افزاری نباید مستقیما باعث redraw شود.

قوانین:

- سنسورها در task مناسب خوانده شوند.
- UI فقط state نهایی و فیلتر شده را بخواند.
- مقدار آنالوگ PLC اگر فقط برای تشخیص سلامت/فعال بودن است، به UI عدد خام نده؛ status بده.
- `temperatureRead` و RTC با timer کند خوانده شوند.
- `analogRead` اگر چند task دارد، با mutex محافظت شود.
- نمونه گیری زیاد ADC باعث لگ UI و گاهی WDT می شود.

## 15) حافظه و PSRAM

PSRAM ظرفیت می دهد، ولی همیشه سرعت نمی دهد.

استفاده پیشنهادی:

- Draw buffer فعال LVGL: RAM داخلی و ترجیحا DMA-capable
- heap LVGL: اول داخلی، بعد PSRAM
- تصویرها و داده های بزرگ کم استفاده: PSRAM یا flash
- فونت های زیاد: با احتیاط، چون render متن فارسی سنگین است
- آبجکت های زنده زیاد: تا حد امکان کم و cache شده

اگر `LV_MEM_CUSTOM` داری، بهتر است allocator اول RAM داخلی را امتحان کند و بعد PSRAM برود. ولی اگر کل heap LVGL به PSRAM برود، UI ممکن است به شدت کند شود.

## 16) راه های تشخیص گلوگاه

### مرحله 1: ثابت کن LCD سالم است

صفحه ساده مثل لوگو یا یک صفحه کم آبجکت را تست کن. اگر `FPS=60` می دهد، گلوگاه LCD خام نیست.

### مرحله 2: اجزای صفحه را گروهی حذف/مخفی کن

موقت و قابل برگشت:

- فقط گیج دما
- فقط گیج زمان اول
- فقط گیج زمان دوم
- فقط نوار پایین
- فقط label ها
- فقط دمو

نتیجه را با `CPU/FPS` ثبت کن.

### مرحله 3: updateهای تکراری را پیدا کن

در کد دنبال اینها بگرد:

```text
lv_label_set_text
lv_obj_set_style
lv_obj_set_pos
lv_obj_set_size
lv_arc_set_value
lv_meter_set_indicator
lv_obj_invalidate
lv_obj_del
lv_obj_create
```

هرکدام که در tick هستند باید شرط تغییر داشته باشند.

### مرحله 4: زمان منطق و رندر را جدا کن

اگر لازم شد، دور این دو بخش زمان بگیر:

- `eez_flow_tick + tick_screen`
- `lv_timer_handler`

اگر منطق سنگین است، مشکل از task/محاسبات/سنسور است. اگر رندر سنگین است، مشکل از invalidate و آبجکت های LVGL است.

## 17) ضد الگوها

اینها در پروژه های HMI با LVGL معمولا باعث کندی می شوند:

- set کردن همه label ها در هر tick
- set کردن font/style ثابت در هر tick
- invalidate کل صفحه برای یک عدد کوچک
- rebuild کردن لیست WiFi یا IO در هر tick
- آپدیت همه گیج ها وقتی فقط یک گیج لمس شده
- خواندن WiFi/RTC/ADC مستقیم داخل tick صفحه
- روشن گذاشتن animation های تزئینی دائمی
- استفاده از PSRAM برای draw buffer فعال
- بازسازی keyboard هر بار بدون نیاز
- مخفی/نمایان کردن مداوم آبجکت بدون تغییر واقعی flag
- استفاده از shadow/opacity/mask زیاد روی آبجکت های پرتکرار

## 18) چک لیست قبل از تحویل هر پروژه

قبل از اینکه نسخه به مشتری یا نصب نهایی برسد:

1. صفحه لوگو یا صفحه ساده باید نزدیک 60 FPS باشد.
2. صفحه اصلی در حالت لمس گیج باید حس فوری داشته باشد.
3. عدد وسط گیج باید همزمان با لمس تغییر کند.
4. باز شدن keyboard نباید با مکث محسوس همراه باشد.
5. شروع/استاپ سیکل نباید باعث محو شدن label های مهم شود.
6. چراغ های پایین باید همان سناریوی واقعی، نیمه روشن و وابسته به خروجی/سنسور را حفظ کنند.
7. صفحه اطلاعات هنگام اسکرول نباید گیر کند.
8. WiFi scan باید SSID واقعی نشان دهد و بعد از خروج طبق تنظیمات به AP/WebApp برگردد.
9. تغییر زبان نباید هر tick همه متن ها را refresh کند.
10. build بدون خطا انجام شود.
11. روی دستگاه واقعی تست شود، چون DMA، رنگ و touch فقط با شبیه سازی قابل اعتماد نیستند.

## 19) نکات حساس همین پروژه

این موارد در پروژه فعلی حساس هستند و هنگام بهینه سازی نباید خراب شوند:

- ظاهر صفحه اصلی و سناریوی سه گیج باید حفظ شود.
- خط چین های گیج ها نباید از نظر ظاهری خراب شوند.
- سه چراغ سیگنال پایین که نیمه روشن/نیمه پر هستند باید دقیق مثل سناریوی تایید شده کار کنند.
- label وسط بالا/زیر Haffler که حالت `F` را نشان می دهد نباید هنگام Start کم رنگ و نامرئی شود.
- تغییر مقدار زمان جوش/خنک کاری باید عدد وسط گیج را فوری آپدیت کند.
- تغییر هدف دما باید مقدار هدف را فوری تغییر دهد، ولی لازم نیست needle دما اگر مهم نیست فشار اضافه ایجاد کند.
- صفحه اطلاعات باید هنگام scroll، update زنده IO را موقتا سبک کند.
- منوی زمان بندی جک وقتی پنل ویرایش باز است، جدول پشت پنل را refresh نکند.
- مسیر DMA نمایشگر بدون تست واقعی نباید دوباره فعال شود، چون قبلا ریسک صفحه سیاه داشته است.

## 20) الگوی نگهداری برای پروژه های بعدی شرکت

برای هر پروژه جدید با همین PLC/HMI، از روز اول این ساختار را رعایت کن:

- برای هر صفحه یک `last_state` داشته باش.
- برای هر label پرتکرار از `set_label_if_changed` استفاده کن.
- برای هر style ثابت از `style_once` استفاده کن.
- برای هر لیست بزرگ، rebuild را فقط هنگام تغییر داده انجام بده.
- برای هر صفحه اسکرولی، هنگام scroll آپدیت زنده را موقتا freeze کن.
- برای هر کنترل لمسی، مقدار اصلی را فوری update کن.
- برای هر sensor/live value، نرخ update مناسب همان سنسور را انتخاب کن، نه نرخ فریم LCD.
- برای هر animation، بپرس آیا واقعا به کاربر کمک می کند یا فقط CPU می خورد.
- برای هر تغییر سرعت، ظاهر و سناریو را قبل و بعد مقایسه کن.

## 21) فرمول تصمیم گیری سریع

اگر صفحه کند است:

```text
آیا LCD در صفحه ساده سریع است؟
  نه: flush، SPI، DMA، buffer، wiring، color swap را بررسی کن.
  بله: مشکل از UI و redraw است.

آیا CPU بالا است؟
  بله: tick، style/text تکراری، سنسور، WiFi، animation را بررسی کن.
  نه: شاید فقط FPS بیکار پایین است و مشکل واقعی نیست.

آیا هنگام لمس یک کنترل فقط همان کنترل کند است؟
  بله: event همان کنترل و آبجکت های وابسته را بررسی کن.

آیا هنگام لمس یک کنترل کل صفحه کند می شود؟
  بله: invalidate یا update سراسری داری.

آیا هنگام scroll کند است؟
  بله: live update را حین scroll freeze کن.
```

## 22) جمله نهایی برای تیم

در HMI صنعتی، سرعت خوب یعنی «حداقل redraw با همان ظاهر». حذف ظاهر آخرین راه است؛ راه حرفه‌ای این است که ظاهر ثابت بماند و فقط همان پیکسل/آبجکتی که واقعاً تغییر کرده به LVGL داده شود.

### 23.2 صفحه اطلاعات — الگوی tick دو سرعت

| مسیر | دوره | محتوا |
|------|------|--------|

### 23.3 کش layout ردیف I/O

`fw_io_row_layout` سنگین است (font measure، 12 dot/row). کش:

- `fw_io_layout_q_code[8][16]` / `fw_io_layout_i_code[8][16]`
- `fw_io_layout_lang`
- `fw_io_sync_all_rows(refresh_names)` در tick

### 23.4 hdr_cover و اسکرول

- `hdr_cover` سفید 48px روی header — جلوگیری از bleed محتوای scroll
- scroll از y=40 شروع می‌شود

### 23.5 invalidate

- تغییر زبان: `apply_language_now` → tick همه صفحات + invalidate فعال
- تغییر تم: فقط `lv_scr_act()` — نه همه objects.screen_*

### 23.6 آپلود سریع

`platformio.ini`:
- `upload_speed = 921600` (قبلاً 115200)
- `upload_protocol = esptool` (`esp-builtin` روی این PC خطا می‌دهد)

**نکته ESP32-S3 + COM17:** زمان نوشتن ~6MB فشرده ≈ 40s (محدودیت USB). برای چرخهٔ توسعه فقط `-t upload` بزن. برای deploy میدانی: OTA.

## حافظه، سرعت و عملکرد
- برد ESP32-S3 با 8MB Flash و بدون PSRAM است. RAM برای LVGL، بافر نمایشگر، فونت‌ها و تصاویر محدود است.
- وضعیت بیلد اخیر حدودا RAM 42% و Flash 65% بود؛ جا هست ولی تصاویر لوگو، فونت‌های فارسی بزرگ و وب‌اپ سریع مصرف را بالا می‌برند.
- در tick هر صفحه از ساختن آبجکت جدید، تغییر متن بی‌دلیل و invalidate بزرگ خودداری کن.
- برای لیبل‌ها از مقایسه متن قبلی یا `set_label_if_changed` استفاده کن؛ `lv_label_set_text` در هر فریم FPS را کم می‌کند.
- اگر style/font در `create_screen...` عوض شد، در `tick_screen...` هم بررسی کن؛ بعضی آبجکت‌ها هر tick دوباره style می‌گیرند و تغییر را برمی‌گردانند.
- فونت فارسی فقط اگر واقعا موجود است استفاده شود. نبود فونت باعث پریدن متن‌ها شده بود.
- DMA/flush نمایشگر حساس است. تغییر در `LV_COLOR_16_SWAP`, `setSwapBytes`, `pushColors`, `pushPixelsDMA` باید با تصویر واقعی تست شود؛ تنظیم اشتباه صفحه را سفید یا رنگی خراب می‌کند.

## کلیدهای پنل و کنترل بدون تاچ
- پنل 10 کلید دارد:
  - ردیف چپ: `F1..F5`
  - ردیف راست: `Save`, `Cancel`, `Mode`, `Start`, `Stop`
- منطق ناوبری در `panel_nav_*` داخل `src/main.cpp` است.
- در صفحه اصلی و خارج از حالت MODE، `Start/Stop` باید استارت/استپ واقعی برنامه جوش باشند.
- وقتی MODE فعال است، `Start` نقش تایید/افزایش و `Stop` نقش کاهش دارد.
- `MODE` باید فقط روی آیتم‌های قابل مشاهده و قابل استفاده بچرخد. آیتم پنهان یا پشت دیالوگ نباید وارد لیست شود.
- برای ارور/راهنما/پیغام‌های مودال، ابتدا دکمه‌های خود دیالوگ را در `panel_nav_collect_for_screen` جمع کن و نوار کناری/آیتم‌های پشت پنجره را حذف کن.
- نگه‌داشتن `Start/Stop` بیشتر از 1 ثانیه باید افزایش/کاهش تکراری بدهد. repeat فعلی در `include/tasks.h` حدود 150ms است و با `panel_nav_focus_is_repeatable()` کنترل می‌شود.
- روی کیبردها: `MODE` بین کلیدها بچرخد، `START` کلید انتخاب‌شده را بزند، `STOP` یک رقم پاک کند.
