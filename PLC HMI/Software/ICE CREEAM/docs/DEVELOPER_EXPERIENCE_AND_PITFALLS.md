# HAFFLER ASTIAJ CM-700 — EXPERT EXPERIENCE, PITFALLS & FIELD TROUBLESHOOTING GUIDE

> **دستگاه بستنی قیفی صنعتی شرکت هافلر (مدل ASTIAJ CM-700)**  
> **کنترلر:** ESP32-S3 N16R8 (16MB Flash, 8MB Octal PSRAM)  
> **نمایشگر و تاچ:** 3.5" ILI9488 Parallel 8080 + Goodix GT911 Capacitive Touch

این سند حاصل تجارب واقعی، ممیزی‌های عمیق مهندسی، حل باگ‌های ریشه‌ای و درس‌آموخته‌های پروژه بستنی‌ساز آستیاج است. هر ایجنت، مهندس نرم‌افزار یا تکنسین نگهداری با مطالعه این راهنما به درک عمیق از خطاهای پنهان، رفتارهای ناشناخته و ترفندهای حیاتی سیستم دست می‌یابد.

## ۱. درس‌آموخته‌های مهندسی سخت‌افزار و فریم‌ور (Embedded Hardware & Firmware Pitfalls)

### ۱.۱. پالس ناخواسته رله‌ها در زمان بوت (Relay Glitch on Startup)
- **شرح مشکل:** رله‌های صنعتی دستگاه Active-LOW هستند (۰ = روشن، ۱ = خاموش). در نسخه‌های اولیه، تعریف پین با `gpio_set_direction(pin, GPIO_MODE_OUTPUT)` باعث می‌شد سطح پین تا زمان فراخوانی فرمان خاموشی صفر بماند. این موضوع یک کلیک شدید و پالس ناخواسته ۱۰ میلی‌ثانیه‌ای به کنتاکتور کمپرسور و پمپ‌ها ارسال می‌کرد که به شدت خطرناک بود.
- **راهکار قطعی:**
  ```c
  // ابتدا سطح پین باید حتماً ۱ شود، سپس جهت آن خروجی گردد:
  gpio_set_level(pin, 1);
  gpio_set_direction(pin, GPIO_MODE_OUTPUT);
  ```

### ۱.۲. فریز ناگهانی تاچ خازنی GT911 بعد از چند دقیقه کارکرد
- **شرح مشکل:** تاچ بعد از حدود ۳۰ ثانیه تا ۲ دقیقه کارکرد کاملاً متوقف می‌شد، در حالی که فریم‌ور و انیمیشن‌های صفحه بدون مشکل رفرش می‌شدند.
- **علت ریشه‌ای:** کنترلر GT911 تا زمانی که بافر قرائت قبلی با نوشتن مقدار صفر در رجیستر وضعیت `0x814E` ریست نشود، اینترلاپت‌های لمس بعدی را تولید نمی‌کند.
- **راهکار قطعی:**
  ```c
  // بلافاصله پس از خواندن بایت‌های تاچ:
  uint8_t zero = 0x00;
  i2c_master_write_to_device(I2C_NUM_0, GT911_ADDR, (uint8_t[]){0x81, 0x4E, zero}, 3, pdMS_TO_TICKS(10));
  ```

### ۱.۳. قفل سخت ۱۸۰ ثانیه‌ای کمپرسور سیلندر اصلی (Anti-Short-Cycle Lock)
- **شرح مشکل:** در صورت نوسان برق یا قطع و وصل دستی کلید استارت، تلاش مجدد کمپرسور پیستونی/اسکرول برای استارت تحت فشار گاز بالا باعث قفل شدن روتور (Locked Rotor Amps) و سوختن سیم‌پیچ کمپرسور می‌شود.
- **راهکار قطعی:** در تسک اسکن PLC، زمان خاموش شدن کمپرسور (`s_comp_last_stop_tick`) در یک متغیر استاتیک ۶۴ بیتی ثبت می‌شود. تابع `plc_comp_can_start()` بررسی می‌کند که آیا حداقل `180,000` میلی‌ثانیه سپری شده است یا خیر. تایمر معکوس باقی‌مانده روی HMI و پرتال وب به صورت ثانیه‌شمار نمایش داده می‌شود.

### ۱.۴. پایش استال مکانیکی با سنسور القایی I0 (Agitator Stall Watchdog)
- **شرح مشکل:** اگر شیر خروجی باز نشود یا مایع بیش از حد منجمد شود (Over-freezing)، ماردون متوقف شده و موتور دچار اضافه بار شدید می‌شود بدون اینکه فیوز بلافاصله قطع کند.
- **راهکار قطعی:** ورودی I0 متصل به سنسور القایی روی پولی گیربکس است. تسک کنترل اگر ببیند رله موتور Q2 روشن است ولی ظرف ۴ ثانیه هیچ اینترلاپت پالسی از I0 نرسیده است:
  1. رله موتور Q2 و کمپرسور Q1 را فوراً قطع می‌کند.
  2. خطای بحرانی `E01_STALL` را صادر و سیستم را قفل می‌کند.

### ۱.۵. افت شدید فریم‌ریت LVGL روی صفحه ۳.۵ اینچ
- **شرح مشکل:** فریم‌ریت از ۵۵ فریم بر ثانیه به کمتر از ۱۸ فریم افت می‌کرد و کشیدن دست روی صفحه لگ داشت.
- **علت ریشه‌ای:** فعال بودن سایه‌های نرم‌افزاری (`lv_style_set_shadow_width > 0`) در استایل‌های ویجت‌های کارت. موتور رندرینگ نرم‌افزاری سایه در رزولوشن ۴۸۰×۳۲۰ بار محاسباتی سنگینی روی هسته ۱ می‌گذارد.
- **راهکار قطعی:** قانون «سایه صفر» (`shadow_width = 0`) برای تمامی المان‌ها وضع شد. رندرینگ کارت‌ها تنها با خط مرزی ۱ پیکسلی شیشه‌ای (`border_width = 1`, `border_color = 0x334155`) اجرا شد که فریم‌ریت را به ۶۰ فریم ثابت رساند.

## ۲. درس‌آموخته‌های پرتال وب و فرانت‌اند (Web Portal Experience & Solutions)

### ۲.۱. نامرئی بودن اعلانات Toast به دلیل توکن‌های رنگی نامعتبر
- **شرح مشکل:** در توابع مختلف پرتال وب کدهایی مانند `showToast("تنظیمات ذخیره شد", "ok")` یا `showToast("خطا", "err")` نوشته شده بود. تابع `showToast` مستقیماً مقدار آرگومان را در `toast.style.background = color` قرار می‌داد؛ در نتیجه مرورگر `'ok'` یا `'err'` را به عنوان رنگ معتبر تشخیص نداده و پس‌زمینه شفاف/سفید نامرئی می‌شد.
- **راهکار قطعی:** یک نگاشت صریح توکن در تابع اضافه شد:
  ```javascript
  var bg = color || 'var(--cyan)';
  if (color === 'ok' || color === 'success') bg = 'var(--green)';
  else if (color === 'err' || color === 'error' || color === 'danger') bg = 'var(--red)';
  else if (color === 'warn' || color === 'warning') bg = 'var(--amber)';
  else if (color === 'blue' || color === 'info') bg = 'var(--cyan)';
  toast.style.background = bg;
  toast.style.zIndex = '100000'; // بالاتر از تمام مودال‌ها
  ```

### ۲.۲. پرش مقدار اسلایدرها و فیلدهای متنی حین تایپ یا درگ کاربر (Polling Race Condition)
- **شرح مشکل:** هر ۱ ثانیه تله‌متری `/api/status` مقادیر جدید را از برد می‌خواند. اگر اپراتور در حال حرکت دادن اسلایدر بلندی صدا (`buzzer-vol-slider`) یا تایپ پین کد بود، فراخوانی ادواری مقدار اینپوت را به مقدار قدیمی برد بازمی‌گرداند.
- **راهکار قطعی:** شرط بررسی فوکوس کاربر (`document.activeElement`) قبل از رفرش هر اینپوت:
  ```javascript
  var elBzVol = document.getElementById('buzzer-vol-slider');
  if (d.buzzer_vol !== undefined && elBzVol && document.activeElement !== elBzVol) {
      elBzVol.value = d.buzzer_vol;
  }
  ```

### ۲.۳. پاک شدن نام‌های سفارشی بستنی‌ها با سوییچ زبان در تب فروش
- **شرح مشکل:** اپراتور در تب POS نام محصولات را به فارسی ویرایش می‌کرد (مثلاً «بستنی توت‌فرنگی دوبل»). با زدن دکمه تغییر زبان به انگلیسی یا ترکی، تابع سوییچ زبان کل جدول محصولات را از روی دیتای استاتیک زبان جدید بازنویسی می‌کرد و نام‌های اختصاصی پاک می‌شدند.
- **راهکار قطعی:** ثبت پرچم `_custom_name: true` در آبجکت محصول ذخیره شده در `localStorage`. اگر این پرچم ست باشد، تغییر زبان نام محصول را بازنویسی نمی‌کند.

### ۲.۴. گم شدن دکمه‌های ذخیره در تب تنظیمات و سردرگمی کاربر
- **شرح مشکل:** در صفحه تنظیمات دستگاه ۴ کارت مجزا وجود داشت: ۱) زمان‌های همزن، ۲) زمان‌های تزریق نازل، ۳) دمای نگهداری مخزن، ۴) تنظیمات عمومی. تنها یک دکمه ذخیره در انتهای کارت چهارم قرار داشت و کاربران متوجه نمی‌شدند بعد از تغییر زمان در کارت اول باید صفحه را به پایین اسکرول کنند.
- **راهکار قطعی:** روی تمامی کارت‌های ۱، ۲ و ۳ دکمه‌های مجزای ذخیره با آی‌دی‌های `btn-save-pdl-timers` و `btn-save-disp-timers` و `btn-save-hold-timers` تعبیه شد و سیستم اعتبارسنجی تغییرات (`markTimersDirty`) تمام دکمه‌ها را به صورت همزمان همگام می‌کند.

## ۳. فرآیند استاندارد ۴ مرحله‌ای قبل از هر خروجی یا ریلیز فریم‌ور

هیچ تغییر یا نسخه‌ای نباید بدون عبور از این ۴ گام تحویل داده شود:

1. **گام ۱ — ممیزی پرتال وب (Web Audit):**
   ```powershell
   python tools/audit_webportal.py
   ```
   *شرط قبولی:* ۰ شناسه گمشده، ۰ تابع جاوااسکریپت نامشخص، تطابق ۱۰۰٪ تگ‌های ترجمه.

2. **گام ۲ — همگام‌سازی فشرده GZIP (Sync HTML to C):**
   ```powershell
   python tools/sync_webportal_html.py
   ```
   *شرط قبولی:* تولید فایل `main/webportal.c` با سایز فشرده ~124KB بدون خطا.

3. **گام ۳ — تست نقاط پایانی شبیه‌ساز (Endpoint Verification):**
   ```powershell
   python tools/test_web_endpoints.py
   ```
   *شرط قبولی:* ۲۰ اندپوینت با کد وضعیت ۲۰۰ و فرمت پاسخ JSON تایید شوند.

4. **گام ۴ — کامپایل موفق فریم‌ور (ESP-IDF Build):**
   ```powershell
   python tools/haffler_icecream_cli.py build
   ```
   *شرط قبولی:* کد خروج صفر (`exit code 0`) و تولید فایل `ili9488_lvgl_btn.bin`.

5. **گام ۵ — همگام‌سازی گراف دانش (AST Graph Update):**
   ```powershell
   graphify update .
   ```
   *شرط قبولی:* استخراج کامل نمادها بدون خطای گسستگی وابستگی‌ها.
