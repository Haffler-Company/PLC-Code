# برنامه آماده‌سازی و ارسال پروژه‌ها به GitHub

این فایل برای مدیریت پروژه‌های شرکت در GitHub ساخته شده است. هدف این است که قبل از آپلود هر پروژه، مشخص باشد چه چیزهایی باید داخل `Code` برود، چه چیزهایی باید در `Projects` به‌عنوان کار/تسک پیگیری شود، و چه چیزهایی بهتر است اصلاً وارد Git نشود.

## پروژه‌های شرکت

| پروژه | وضعیت بررسی | پیشنهاد ساختار GitHub | توضیح |
|---|---|---|---|
| PLC | بررسی اولیه انجام شده | repository جدا یا monorepo فعلی `PLC` | شامل PLC 5K، PLC 8K، PLC 10K و PLC HMI |
| آسیاب قهوه | هنوز بررسی نشده | repository جدا | قبل از آپلود باید ساختار فایل‌ها بررسی شود |
| CodeRun | هنوز بررسی نشده | repository جدا | نیازمند README، مستندات فنی و پاک‌سازی فایل‌های خروجی |
| آواتایم | هنوز بررسی نشده | repository جدا | اگر چند نسخه/مشتری دارد، release و changelog جدا لازم است |

## فرق Code و Projects در GitHub

- `Code`: محل آپلود فایل‌های واقعی پروژه، سورس، مستندات، شماتیک، PCB، BOM، README و فایل‌های لازم برای ساخت/تولید.
- `Projects`: محل مدیریت کارها، باگ‌ها، تسک‌ها، وضعیت اصلاحات و برنامه آینده.
- `Releases`: محل قرار دادن خروجی‌های آماده مثل firmware نهایی، فایل zip نسخه رسمی، PDF خروجی تولید یا package تحویل.
- `Issues`: محل ثبت مشکل، درخواست تغییر، باگ و کارهای کوچک‌تر.

## پیشنهاد ساختار کلی شرکت

برای شرکت بهتر است هر محصول یا خانواده محصول repository جدا داشته باشد:

```text
Haffler-PLC
Haffler-Coffee-Grinder
Haffler-CodeRun
Haffler-AvaTime
Haffler-Product-Docs
```

اگر پروژه‌ها خیلی به هم وابسته هستند، می‌شود repository مادر هم داشت:

```text
Haffler-Products/
├── PLC/
├── Coffee-Grinder/
├── CodeRun/
└── AvaTime/
```

اما برای GitHub، مدیریت نسخه، حجم فایل‌ها و دسترسی افراد، repository جدا برای هر خانواده محصول معمولاً تمیزتر است.

## چک‌لیست قبل از آپلود هر پروژه

### 1. مستندات پایه

- [ ] `README.md` اصلی پروژه کامل باشد.
- [ ] هدف محصول و کاربرد صنعتی آن توضیح داده شود.
- [ ] ساختار پوشه‌ها توضیح داده شود.
- [ ] آخرین نسخه سخت‌افزار و نرم‌افزار مشخص باشد.
- [ ] روش build/compile نوشته شود.
- [ ] روش flash/program نوشته شود.
- [ ] فایل‌های مورد نیاز تولید و خدمات مشخص باشند.
- [ ] فایل `FIXES.md` یا `CHANGELOG.md` برای اصلاحات وجود داشته باشد.
- [ ] فایل `GENERAL_RULES.md` یا قوانین همکاری وجود داشته باشد.
- [ ] فایل `KNOWLEDGE.md` برای دانش فنی پروژه وجود داشته باشد.

### 2. ساختار پوشه‌ها

- [ ] پوشه `Docs` برای مستندات.
- [ ] پوشه `Hardware` برای فایل‌های سخت‌افزار.
- [ ] پوشه `Software` برای سورس و نسخه‌های نرم‌افزار.
- [ ] پوشه `Release` یا `Releases` برای خروجی‌های رسمی.
- [ ] پوشه `Manufacturing` برای فایل‌های تولید، در صورت نیاز.
- [ ] پوشه‌های خالی یا حذف شوند یا داخلشان `README.md` توضیحی قرار گیرد.
- [ ] نام پوشه‌ها تا حد ممکن انگلیسی، استاندارد و بدون غلط املایی باشد.

### 3. فایل‌هایی که بهتر است داخل Git باشند

- [ ] سورس کد اصلی.
- [ ] فایل‌های پروژه IDE/PlatformIO/Arduino، اگر برای build لازم هستند.
- [ ] شماتیک و PCB اصلی.
- [ ] BOM.
- [ ] دیتاشیت اختصاصی محصول.
- [ ] عکس محصول در حجم مناسب.
- [ ] PDF یا HTML خروجی شماتیک برای مشاهده بدون نرم‌افزار تخصصی.
- [ ] README و دانش فنی.
- [ ] فایل‌های pin map.
- [ ] فایل‌های flash address.
- [ ] release note هر نسخه.

### 4. فایل‌هایی که باید با احتیاط آپلود شوند

- [ ] فایل‌های `.bin` فقط اگر release رسمی هستند.
- [ ] فایل‌های `.zip`, `.rar`, `.7z` فقط اگر واقعاً آرشیو release هستند.
- [ ] PDFهای حجیم فقط اگر ضروری هستند.
- [ ] عکس‌های کاتالوگ حجیم بهتر است فشرده یا جداگانه نگهداری شوند.
- [ ] کتابخانه‌های آماده/vendor شده فقط اگر نسخه دقیقشان برای build لازم است.

### 5. فایل‌هایی که معمولاً نباید داخل Git باشند

- [ ] پوشه `.pio`
- [ ] پوشه `build`
- [ ] پوشه `Build` خروجی کامپایل، مگر در release رسمی
- [ ] فایل‌های `.elf`
- [ ] فایل‌های `.map`
- [ ] فایل‌های object/cache
- [ ] فایل‌های موقت Altium مثل `__Previews` و `History`
- [ ] فایل‌های سیستم‌عامل مثل `Thumbs.db` و `.DS_Store`
- [ ] `.git` داخلی داخل زیرپوشه‌ها

### 6. امنیت

- [ ] رمز WiFi واقعی حذف یا sample شود.
- [ ] token، password، license key و اطلاعات مشتری حذف شود.
- [ ] کدهای اضطراری یا master passwordها قبل از public شدن بررسی شوند.
- [ ] اگر پروژه private است، باز هم دسترسی افراد محدود و مشخص باشد.

## تصمیم پیشنهادی برای آپلود

برای شروع:

1. پروژه PLC را در همین repository فعلی کامل و private نگه دارید.
2. برای هر پروژه دیگر repository جدا بسازید.
3. همه repositoryها را داخل GitHub Organization شرکت قرار دهید.
4. برای هر repo یک GitHub Project جدا یا یک Project کلی شرکت با field به نام `Product` بسازید.
5. فایل‌های release سنگین را در GitHub Releases یا Git LFS بگذارید، نه داخل مسیر سورس.
